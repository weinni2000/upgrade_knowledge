# base_geoengine: 19.0 -> 20.0

| Title | Explanation | Odoo Commit Hash |
| --- | --- | --- |
| `Query` moved out of `odoo.tools` | `from odoo.tools import Query` no longer works; `Query` now lives in `odoo.orm.query` and is re-exported from `odoo.models` (`from odoo.models import Query`). | [`ef789d3c50869ccb8651b7056c725257eb069759`](https://github.com/odoo/odoo/commit/ef789d3c50869ccb8651b7056c725257eb069759) |
| `Domain._to_sql()` / `Field.condition_to_sql()` signature reworked around `TableSQL` | Domain SQL generation no longer takes separate `(model, alias, query)` positional args. `Domain._to_sql(self, model, alias, query)` became `_to_sql(self, table)`, and `Field._condition_to_sql(self, field_expr, operator, value, model, alias, query)` became `condition_to_sql(self, table, field_expr, operator, value)`. `table` is a `TableSQL` (`odoo.orm.query.TableSQL`) bundling the model (`table._model`), alias (`table._alias`) and the owning `Query` (`table._query`); build one from a `Query` via its `.table` property, or rebind the model with `table._with_model(other_model)`. Any code monkey-patching `DomainCondition._to_sql` or `fields.Field._condition_to_sql` (e.g. to add custom domain operators) must be adapted to this new signature. | [`5521c6b3f30740b0d76b98eab3b507eff9f1cfb8`](https://github.com/odoo/odoo/commit/5521c6b3f30740b0d76b98eab3b507eff9f1cfb8), [`ba98a13f9712d8a3aad19b5e22fe8ec23d852ef1`](https://github.com/odoo/odoo/commit/ba98a13f9712d8a3aad19b5e22fe8ec23d852ef1) |
| `ir.rule` + `ir.model.access` merged into `ir.access` | Both models are gone; access control and record rules are now a single `ir.access` model. Field mapping: `ir.model.access.perm_read/write/create/unlink` (booleans) -> `ir.access.operation` (a `crud`-subset string, e.g. `"r"`, `"cru"`) with compat `for_read`/`for_write`/`for_create`/`for_unlink` booleans; `ir.rule.domain_force` (Char) -> `ir.access.domain` (Char); `ir.rule.groups` (Many2many) -> `ir.access.group_id` (single Many2one, one row per group). **Combination semantics changed**: an access row WITH a `group_id` is a *permission* (all matching permissions across a user's groups are OR-ed); an access row WITHOUT a `group_id` (global) is a *restriction* (all restrictions are AND-ed for everyone, regardless of group). This is NOT the same as old `ir.rule`'s "OR domains from groups the user belongs to, AND with global rules" — in particular, granting one group a broad/unrestricted permission (no domain) on a model means ANY user who is also in that group gets that unrestricted access via OR, even if they're also in a more restricted group. To test "group A sees everything, group B sees a subset" you need the two groups to be *disjoint* (no user in both), otherwise the broader permission always wins. Custom code calling `model.env["ir.rule"]._compute_domain(model_name, operation)` should call `model._access_domain(operation)` instead (mirrors what `BaseModel._search()` itself does). | none (renamed/merged in a local pre-release core checkout, no single public commit) |
| `BaseModel._check_field_access()` deprecated | Renamed to the public `check_field_access()` (same signature/behavior); the old name still works but emits a `DeprecationWarning`. | none (see `odoo/orm/models.py`, `@deprecated("Since 20.0, use check_field_access()")`) |
| `Query.add_where()` / `Query.subselect()` deprecate plain strings | Passing a raw SQL string (not an `SQL(...)` object) to `Query.add_where()` or `Query.subselect()` now emits `DeprecationWarning: Since 20.0, use only SQL in the where clause` / `"Since 20.0. select takes only SQL arguments"`. Wrap any raw string in `SQL(...)` before passing it. | none |
| `Cursor.mogrify()` / `execute()` take an `SQL` object directly | `SQL` objects no longer expose `.code`/`.params` attributes (they're bundled in a private `_sql_tuple`). `cr.mogrify(sql_obj.code, sql_obj.params)` breaks with `AttributeError: 'LiteralSQL' object has no attribute 'code'`. Pass the `SQL` object straight to `cr.mogrify(sql_obj)` / `cr.execute(sql_obj)` instead (both accept an `SQL | str` first arg and assert `params is None` when given an `SQL`). | none |
| Owl 2 -> Owl 3: entire JS framework rewritten | Odoo 20.0 replaces Owl 2 with Owl 3. A temporary bridge, `odoo/addons/web/static/src/owl2/owl3_compatibility_layer.js`, patches some of the gap and documents the required manual changes. Read it in full before porting any custom Owl component. One broken top-level import in a module's JS (e.g. calling a now-removed function at import time) crashes Odoo's ES module loader for the **entire** asset bundle (`web.assets_backend`/`web.assets_web`), breaking every page, not just the view that owns the broken file — always verify by loading an unrelated page/tour, not just the module's own views. Concrete API changes hit by this module: `reactive(obj)` removed, replaced by `proxy(obj)` (same underlying Proxy-based reactivity, just renamed); `reactive(store, callback)` (subscribe-with-callback form) has no replacement — use `effect(callback)` instead (runs immediately once, then on every dependency change; register `onWillUnmount` for its cleanup function, and create the `effect()` itself in `onMounted` if it depends on things only set up post-mount); `useState()` is removed (any `proxy()`-wrapped object read during render is auto-tracked, no wrapper hook needed); `useRef("name")` is removed — `t-ref="name"` now binds to a plain instance property literally named `name` that must itself be a signal (has `.set()`); reading the ref's element is `this.name()` instead of `this.name.el`; `onRendered()` is removed with no direct replacement (combine `onMounted()` + `onPatched()` if you need "after every render, initial and subsequent"); static/class-level `Component.props` and `Component.defaultProps` are no longer supported — the `Component` constructor throws if either is set ("Declare the props schema through useProps() instead") — replace with `this.props = useProps(schema)` (or a schema-less `useProps()`) inside `setup()`; `useEffect()` still exists but changed timing semantics — the compat layer's `useLayoutEffect` (import from `@web/owl2/utils`) preserves the old Owl-2-like timing; manually creating `new App(Component, config); app.mount(target)` no longer matches Owl 3's real `App`/`createRoot` API split — use the compat layer's `mount(Component, target, config)` helper instead, which takes the old flat config shape. | none (architecture migration, not a discrete commit — see `owl3_compatibility_layer.js` in core) |
